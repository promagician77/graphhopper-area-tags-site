    Same routes as the polygons

    Each of the 27 journeys was routed with the same rule written two ways: polygons sent in the request (in_newport) and tags worked out at import (area_newport). All 27 pairs match exactly. Every coordinate, the distance, the time and the route weight are identical, in flexible mode and with landmarks (27 of 27).

    The test has teeth: the rule changes the route on 14 of the 27 journeys compared with no area rule, so a wrong tag would show.

    The rule: priority ×0.7 in the AONB, ×0.4 in Newport, ×0.2 in Seaview, and speed limited to 30 km/h in Ryde, on GraphHopper's own car profile.

    10.3× less routing time

    With polygons in the request, GraphHopper builds a prepared polygon for each area on every request, then tests every edge the search touches against it. With tags, the same check is reading 4 bits already stored on the edge.

    The 27 journeys took 817 ms with polygons and 80 ms with tags (sum of per-journey medians, 25 runs each, flexible mode). The slowest single route fell from 49.9 ms to 6.2 ms. With landmarks the gain was 9.1×.

    Before any routing, the polygon request also has 250,777 bytes of areas JSON to parse: 3.3 ms in GraphHopper's own mapper, against 0.004 ms with tags. That cost is not included above.

    What the 1.3× target is measured against

    Reading the tags costs almost nothing: 0.65 µs per road visited, against 0.63 µs with no area rule. Polygons cost 6.62 µs.

    The rule itself costs more than the check. Lowering priority inside the areas makes the search visit 1.52× as many roads overall, and up to 3.1× on one journey. The same happens with polygons, because the search is identical.

    So the answer depends on the baseline. Tags alone, measured with the same statements switched off (area_newport && false), came to 1.13× overall and at most 1.27× on any journey. With the rule active it was 1.56× overall, and 18 of 27 journeys were above 1.3×. All 18 were journeys where the rule makes the search visit more roads.

    Your rules and test journeys will decide where this lands. I would agree which baseline counts before quoting a pass.

    Why not GraphHopper's built-in custom areas?

    GraphHopper already reads area files at import (custom_areas.directory). It looks each edge up by one point: its middle point (OSMReader.setArtificialWayTags). Request-time areas instead ask whether the polygon touches the edge anywhere. Wherever an edge crosses or touches a boundary, the two can disagree.

    I built that version too and ran it on the same journeys. 801 edges disagreed with the request-time test, 475 of them car roads. 5 of the 27 journeys came back with a different time or distance, and 2 took a different path:

    • : 13.48 km by polygons, 14.50 km by the shortcut
    • : 27.14 km by polygons, 24.49 km by the shortcut

    The tags here run GraphHopper's own whole-edge test on the stored geometry during import, so they agree by construction, and the check after import proves it.

    One point against the whole edge

    Two more details copied exactly: GraphHopper's quick reject uses the box of the edge's two end nodes only, and the test runs on coordinates rounded to the 1e-7 degree precision the graph stores. Unit tests cover both against CustomWeightingHelper.in, plus over 15,000 random edges on concave polygons, some with holes.

    How it plugs into your server

    The plugin is five small Java classes. It registers area_<id> yes/no values and a parser that sets them while edges are created, so you still import with the normal command.

    GraphHopper's web server creates new GraphHopper() itself, so it needs a five-line patch to pass in the area file. Requests then use area_newport where they used in_newport. The prefix cannot be in_, because GraphHopper 11 rejects encoded value names that start with it.

    The four tags fit in spare bits: edge flags stayed at 7 bytes and the graph grew by 1,414 bytes. Import time on the island was 0.9 s without tags and 0.9 s with them, which is within run-to-run noise.

    Checks on the build itself

    My sandbox cannot reach Maven Central, so GraphHopper 11.0 was compiled from its git tag against Ubuntu's library jars, including HPPC 0.7.2 instead of 0.8.1. Before trusting any timing from it, I ran GraphHopper's own test suites on this build.

    The only source not compiled is the optional legal-speed calculator, which needs a Kotlin library; it is off by default and was replaced by a stub that fails if called.

    • 2,574 passGraphHopper 11.0's own core and web-api tests on this build: 0 failed, 16 skipped upstream, 2 stopped by their own assumptions (for example "loop shortcuts only exist for edge-based CH").
    • 12 passPlugin tests: crossing, touching, bending and rounded edges, rectangles, holes and multipolygons, random edges, bad names and invalid polygons, plus a second dataset (Andorra, from GraphHopper's test files) with 0 disagreements.
    • IdenticalThe patched GraphHopperManaged started from a server-style config and answered real POST /route JSON bodies: Ryde → Easton, 30.59 km, same route before and after.
    • 2020-07-21Isle of Wight extract from Geofabrik, 6.9 MB, 43,356 junctions and 50,573 edges. Boundaries are OSM relations: three civil parishes and the AONB.
